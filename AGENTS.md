# MediaHub project guide

## Stack and entry points

- Next.js 16.2.1 / React 19.2.4 as declared in `package.json`; App Router, TypeScript (strict, `@/*` → `src/*`), Tailwind CSS 4, and shared UI primitives in `src/components/ui/`.
- `src/app/layout.tsx` installs the tRPC/React Query provider, tooltip provider, toast UI, global styles, and Google fonts. `src/app/page.tsx` is the public marketing landing page; its sections live in `src/components/landing/`.
- `src/app/(dashboard)/layout.tsx` wraps pages in `DashboardShell` and an error boundary. The shell provides brand selection; `src/components/layout/Sidebar.tsx` and `src/components/common/ModeSwitcher.tsx` expose click, chat, and analytics modes. Route groups do not appear in URLs.
- Frontend queries/mutations use `trpc` from `src/lib/trpc/client.ts`, backed by `/api/trpc`. `src/lib/hooks/use-user.ts` provides the current profile; `use-brand.tsx` selects the active brand and invalidates queries when it changes. Keep brand-dependent query inputs and mutation invalidation consistent.

## Features and code map

- **Media and publishing:** `/library`, `/upload`, `/publish/[groupId]`, `/calendar`, and `/queue`; components in `src/components/media/`, `publish/`, and `calendar/`. Uploads go through `/api/upload` to Google Drive, with Supabase asset/group metadata and queued categorization. Sharp reads image metadata; video metadata uses ffprobe when available. Publishing supports drafts, action/account selection, per-job text, scheduling, and duplicate-job checks. The current `PublishPanel` operates on the group's first asset. Check `src/server/services/media/rules-engine.ts`, the publish router, and worker handlers together when changing platform actions.
- **Accounts and administration:** `/accounts`, `/brands`, `/brands/new`, `/settings`; platform OAuth callbacks under `src/app/api/callback/`, Drive connections, platform credentials, users/invitations, audit logs, LLM configuration, and Instagram/Facebook sessions. Sidebar visibility is not authorization.
- **Chat:** `/chat`, `src/components/chat/`, and `src/server/services/chat/`; LLM tool definitions and the executor connect chat actions to media, scheduling, and other studio operations. Preserve role checks in both tool availability and execution.
- **Analytics:** `/analytics` plus `posts`, `intelligence`, `sentiment`, `competitors`, `best-times`, and `export`; `src/server/trpc/routers/analytics.ts` serves metrics, history, predictions, recommendations, sentiment, competitor data, and exports. Background fetches and LLM-dependent analysis live in `worker.ts`.
- **Comment inbox:** `/threads` and `src/components/threads/ThreadsInbox.tsx`; comment synchronization, thread/status management, reply templates, generated replies, bulk replies, and auto-reply settings use the threads router and queue workers.
- **Social data tools:** public `/instagram` and `/facebook` pages contain substantial client-side TSX and distinguish anonymous demo requests from authenticated fetches. Instagram includes profile/content and hashtag fetching with CSV exports; Facebook includes page/profile/group/post fetching and CSV exports. Export helpers are `src/lib/insta-export.ts` and `src/lib/fb-export.ts`. Dashboard routes `/insta-fetcher`, `/insta-comments`, `/fb-fetcher`, and `/fb-scraper` also exist. Trace each page's actual tRPC calls: the public Facebook page currently uses `fbSession`, while Instagram uses `instaFetcher`.
- Scraping services live in `src/server/services/instagram/` and `facebook/`; Facebook includes browser/session fetchers and caching. Browser scraping needs Chromium (`CHROMIUM_PATH` in Docker). Results depend on sessions, platform restrictions, credentials, and optional proxies; UI copy is not proof of successful extraction.

### Facebook Photos and Reels collections

- The public Facebook tool sends `contentTypes: [posts, reels]` (either or both), plus independent `photoLimit`/`reelLimit`, through `fbSession` to `src/server/services/facebook/media-grid.ts`. Both selected collections run in separate contexts sharing one Chromium process. Single `contentType` remains supported; legacy callers without a media type still use `browser-fetcher.ts`. Posts means the owner's Photos grid; Reels uses the owner's Reels grid. Do not route these collections back through the mixed activity-card parser.
- Media-only results include unique media IDs, Facebook links, thumbnails, and visible reel views. Captions, dates, likes, comments, and video files are not established by grid extraction. `metricsAvailable: false` prevents unknown metrics from rendering/exporting as observed zero. Optional comments/replies begin through a separate protected job after media renders; they never delay initial media results.
- Snapshots are isolated by session hash, collection, target and requested count, with five-minute expiry and explicit refresh. Incomplete/empty grids are not cached as successful full pulls. Response metadata identifies capture time, cache use, requested/returned counts and why scrolling stopped. Fresh Facebook results can change; cached snapshots are historical data, not a completeness guarantee.
- The Facebook UI saves to native Google Sheets through protected `exportDestinations` / `saveMediaSheet` endpoints, instead of offering CSV download controls. `media-drive-export.ts` uses the selected brand's existing Drive OAuth/root and a sibling `Facebook scraper` folder beside Originals/Processed. One Sheet per organization, brand and normalized Facebook profile contains Photos/Reels tabs with the same shared headers (`FB_MEDIA_COLUMNS` / `buildFbMediaRows` in `fb-export.ts`). Stable run IDs prevent repeated progress updates from creating extra files. Media rows merge by collection + media ID; comments/replies merge by comment ID, retaining earlier data when a newer response is partial. Blank unavailable values never erase known values; observed zero is real data. No sharing permissions are changed.
- Sheet availability is verified on every save (`media-drive-target.ts`). A trashed, missing, moved, non-Sheet or read-only cached destination is discarded as a pointer only. Search the current export folder for the exact organization/brand/profile and verify search candidates before reuse; otherwise create a new native Sheet. Never restore or move removed user files. A destination lost during writing/verification gets one bounded recovery within the existing brand lock. Auth, quota, transient network failures, corrupted managed headers and ambiguous creation are not reasons to create duplicates. Live recovery on 2026-09-06 saved Photos, appended Reels to the same Sheet, and reused it on a repeated save. Later user removal and another user run produced another valid replacement with both 12-row tabs. New Sheets contain the retained run data, not inaccessible history from removed files.
- Google Sheets receives media first, then the completed/cancelled background details snapshot. If a Drive brand is selected when fetching starts, `startMediaComments.sheetExport` pins that authorized brand, run ID and exact media set; `media-sheet-job.ts` saves the terminal snapshot on the server even when the browser page closes. Progress exposes `sheetSave` and the UI polls until saving finishes, with a same-run manual retry on failure. A brand chosen after the run starts uses client-driven saving and requires keeping that page open. Neither path survives an app process restart during unfinished retrieval.
- Oversized cells (notably Comments JSON) continue in numbered columns with identical headers across both tabs; concatenation is lossless. Continuation-column positions remain stable across saves, with new columns appended so interrupted batches can be retried without corrupting older JSON. Preserve these managed headers. Existing rows are read and merged before writes, with bounded storage and explicit failures rather than truncation. The app uses RAW cell values so scraped captions cannot become formulas.

## Backend and auth boundaries

- Local Chrome Facebook session import: `npm run fb:session:chrome -- --chrome-account <exact Chrome email> --local-demo` runs the macOS host helper in `scripts/facebook/import_chrome_session.py` (usage in `scripts/facebook/CHROME-SESSION.md`). It reads only the selected profile's five Facebook auth cookies, verifies the account with isolated Selenium Chrome, then refreshes the same account through existing protected session endpoints. Dependencies live outside the repo in the user's cache. It does not restart the app, scrape media, write Google Sheets, or schedule recurring imports. The normal Chrome profile stays open; default-profile remote debugging is not enabled. Live import on 2026-09-07 verified the requested Chrome account and refreshed the existing dead session to active on port 3010 without adding a row. Seven focused offline checks passed; this is session-validation evidence, not a new scrape/completeness test.

- `src/server/trpc/router.ts` registers routers and builds auth/profile context; `index.ts` defines protected/role procedures and brand-access helpers. Database access is in `src/lib/supabase/`; `getDb()` uses privileged server access, so retain explicit organization/brand filters and authorization checks.
- `src/proxy.ts` delegates session handling to `src/lib/supabase/middleware.ts`. `/api/*` is deliberately excluded from its matcher to avoid multipart upload-body corruption; API handlers authenticate themselves.
- Current local open-studio behavior sends logged-out dashboard visitors through `/api/studio-enter`, which signs in as a local demo admin and redirects to the requested page. Login/signup/reset pages remain. This is an explicit local-demo behavior, not a production access-control model.
- `worker.ts` is the separate BullMQ worker entry point: publishing, analytics/history, token refresh, categorization, sentiment, competitor/trend tasks, and comment synchronization/replies. Queue producers are in routers/services and `src/server/queue/`. A running Next server alone does not execute queued work.
- Schema: `src/server/db/schema.sql`; migrations: `supabase/migrations/`; local bootstrapping: `scripts/docker-init.sh` and `supabase/init/`. Inspect migration order/content before database changes. Do not expose `.env*`, session cookies, OAuth tokens, encryption keys, or local certificate keys.

New account connections use the app's OAuth consent flow and `/api/callback/google-drive`; select the intended brand/account before changing a connection. Finding local credentials is not authorization to upload, share, delete, or broaden access.
- For discovery, return only field names and presence/status, not secret values. Avoid the `credentials.list` tRPC endpoint for presence checks: it returns decrypted secrets to super-admin users. `drive.verify` is also not read-only: it tests folder creation/upload/read and may update brand setup status.

## Running locally

Check existing listeners and Docker containers before starting anything; do not stop another project's server to free a port. The current Compose configuration is authoritative over older README/script URL banners.

| Workflow | Command / behavior |
| --- | --- |
| Docker development with hot reload | `bash dev.sh` (base Compose plus `docker-compose.dev.yml`); `bash dev.sh --build` after dependency changes |
| Start existing Compose services without rebuilding | `docker compose up -d` (base production configuration) |
| Rebuild production app and worker | `bash restart.sh`; requires infrastructure already running |
| Full startup/bootstrap | `bash start.sh`; stops the Compose stack, may fetch/pull Git updates, then builds/starts it. `scripts/start.sh` delegates here |
| Logs | `docker compose logs --tail=100 app worker caddy` (add the dev overlay when inspecting dev configuration) |
| Host development | After `npm ci` and local environment/infrastructure setup: `npm run dev`, `npm run ssl-proxy`, `npm run worker:dev`; `npm run dev:all` launches all three |

- **Docker URLs:** `https://localhost:3443` through Caddy → `app:3000`; direct app HTTP is **`http://localhost:3010`** (`3010:3000`). Supabase gateway: `54321`; database: `54322`; Studio: `54323`; test email UI: `54324`; Redis: `6379`.
- **Host npm workflow:** Next defaults to HTTP `3000`; `ssl-proxy` forwards HTTPS `3443` to `3000` using `localhost+1.pem` and `localhost+1-key.pem`. Do not launch that proxy when Docker Caddy already owns `3443`, or point it at an unrelated app on `3000`.
- Docker CLI must be on PATH and its daemon responsive. On macOS the CLI may exist at `/Applications/Docker.app/Contents/Resources/bin/docker` even when `docker` is missing from PATH.
- Docker dev bind-mounts source, with separate container volumes for `node_modules` and `.next`. If host dependencies/docs are absent, read the required Next guides inside the development container or install locked host dependencies before code changes.
- The app/worker require Supabase and Redis configuration; inspect the example env files for names without printing actual secrets. Drive/OAuth/LLM features need their own configured connections or keys. Container-internal Supabase URLs differ from browser-facing URLs. Docker production bakes `NEXT_PUBLIC_*` values during build.
- `start.sh --reset` and `docker compose down -v` destroy local data; do not use them for routine startup or recovery.

## Validation and editing

- User preference: for a localized change, run the affected regression tests and necessary live integration checks. Do not rerun the entire suite by default; broaden only for cross-cutting changes, failures or unresolved concerns.
- Latest instruction for the export count-highlighting change: code/deployment only; do not manually modify the existing Sheet or run new backend/live tests. The user will do the final frontend test. The current schema has one paired actual/retrieved metric: Comments Count (Reported) / Comments Scraped Count. Future app-triggered Sheet saves install a conditional rule highlighting only the scraped cell red when it is lower than the available numeric reported count. Blank unavailable counts are not zero; equal or higher scraped values remove the conditional red appearance automatically. Preserve unrelated rules and replace the app's marked rule without duplicates. Do not automatically replay index-based formatting requests after ambiguous responses.
- Use `npm run lint` (or targeted ESLint), `npx tsc --noEmit`, and `npm run build` as appropriate. There is no test script in `package.json`; root `.mjs` probes and `scripts/` include ad hoc tools, not a general automated suite.
- `next.config.ts` sets `typescript.ignoreBuildErrors: true`; a successful build does **not** establish type correctness. It also uses standalone output and externalizes `playwright-core`.
- For frontend changes, verify the affected route, loading/error/empty states, brand changes, and relevant tRPC requests. For queued operations, inspect worker results as well. Distinguish code-inspected features from live-tested integrations.
- Preserve existing uncommitted work. Limit changes to the requested scope; avoid unrelated scraper outputs, probes, or dependency updates.
